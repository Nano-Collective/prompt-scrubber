Fix `watch` destroying data by reusing one placeholder for two different values. Each tick called `handleScrub` with no session ID, so `SessionManager` minted a fresh UUID and started from an empty map; the per-category counter reset to `1` every tick while the file on disk still held «Email_1» from the previous one. The next tick reissued that same token for a different address and wrote it back over the only copy, so both rehydrations were confidently wrong and the distinction was unrecoverable - and a session file accumulated per tick with no ID ever printed to say which one to rehydrate from. `handleWatch` now allocates a single session for the whole run (reusing `--session-id` when given), threads it through every clipboard and file tick, and prints `[watch] Session ID: <id>` on start-up. Each tick's log line and notification are now driven by that scrub's own stats rather than the session map, so a long-running watcher reports what it just replaced instead of the running total. The underlying hazard is fixed in the core too: `createPlaceholder` now skips any candidate name that already appears literally in the text being scrubbed, so re-scrubbing scrubbed output no longer collapses a literal «Email_1» and a real address into one token. Thanks to @addyCooks. Closes #124.
